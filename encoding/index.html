Text Encoding Explorer

How computers turn the letters you type into numbers — and why that matters for cybersecurity.

What's going on here?

Computers don't store letters — they store numbers. ASCII (American Standard Code for Information Interchange) is a 7-bit code, published in 1963, that assigns every English letter, digit, and punctuation mark a number from 0–127. Your keyboard sends a character, the computer looks up its number, and that number is stored as binary (base 2) and is often written out in hexadecimal (base 16) because hex is a compact, human-friendly way to represent groups of bits.

Type or paste something below. Each character becomes one byte (8 bits). Hover over any character — in your text, in the binary, in the hex, or in the reference table — and every matching occurrence lights up everywhere else, so you can see the connection.

  • Why it matters for security: file signatures, buffer overflows, encoding-based injection attacks, and log/packet analysis all require reading raw bytes, not just text.
  • Encoding ≠ encryption: ASCII is a public, fixed lookup table — anyone can decode it. It hides nothing; it's just a format.
  • 128 vs 256: standard ASCII only defines 0–127. Codes 128–255 ("extended ASCII") are not standardized the same way across systems — a common source of mojibake and interoperability bugs.

What's going on here?

ASCII only has 128 codes — nowhere near enough for the world's languages, symbols, and emoji. Unicode solves this by giving every character in every writing system its own number, called a code point (written U+0041 for "A"). There are over 1.1 million of them.

UTF-8 is the encoding that turns a code point into actual bytes. It's designed so plain English text still costs exactly what ASCII costs — 1 byte per character — but every code point outside that range costs more: 2, 3, or 4 bytes. Type something with accents, non-Latin scripts, or emoji below and watch the byte cost climb.

  • The tradeoff: supporting every character on Earth means most non-English, non-ASCII text takes up more space than plain ASCII — often 2–4× as much.
  • Why it matters for security: visually identical characters from different scripts (Cyrillic а vs. Latin a) have different code points — a classic trick behind homoglyph phishing domains and lookalike usernames.
  • Backward compatible: because UTF-8 encodes ASCII characters exactly as ASCII does, every plain ASCII file is already valid UTF-8.

What's going on here?

ASCII and UTF-8 both spend a fixed number of bits per character — the letter "e" (extremely common in English) costs exactly as much as "z" (rare). Huffman coding asks: what if common symbols got shorter codes, and rare symbols got longer ones?

Type something below and it's scanned for how often each character appears. A binary tree is then built by repeatedly combining the two least-frequent symbols into one, until a single tree remains. Walking from the root to a symbol's leaf — left = 0, right = 1 — gives that symbol's code, so frequent symbols (near the top) get short codes and rare ones (buried deep) get long ones.

  • No code is a prefix of another — this "prefix property" is what lets a decoder read the bitstream one symbol at a time, with no separators and no ambiguity.
  • The payoff: even though rare symbols get codes longer than ASCII's flat 8 bits, the common ones get much shorter — the total is almost always smaller.
  • A security wrinkle: compressed size leaks information about repeated patterns in the input. Attacks like CRIME and BREACH exploited HTTP/TLS compression to steal secrets (like session cookies) from encrypted traffic, byte by byte.
